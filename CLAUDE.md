# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Bearded Theme: a color theme extension for **VS Code** and **Zed**, 60+ variants (dark, light, high-contrast, colorblind-safe). TypeScript, ES modules, no bundler — `vite-node` executes `.ts` files directly. No runtime app code: the entire `src/` tree is a build-time generator that turns theme definitions into JSON theme files.

## Git

Never `git commit` or create branches on your own — the user handles all commits and branching themselves.

## Commands

```bash
npm run build              # build both VS Code and Zed themes
npm run build:vscode       # VS Code only -> dist/vscode/themes/*.json (one file per theme)
npm run build:zed          # Zed only -> dist/zed/themes/bearded-theme.json (one file, all themes)
npm run dev:vscode         # nodemon watch, rebuilds VS Code themes on save
npm run dev:zed            # nodemon watch for Zed

npm run lint               # eslint check, no fixes
npm run fix                # eslint --fix (this is the formatter; there is no Prettier)
npx tsc --noEmit           # typecheck (no test suite exists in this repo)

npm run bump:version <vscode|zed|all> <major|minor|patch>   # see Versioning below
npm run create:release-notes                                  # scaffold releases/{version}.md
npm run build:ext:vscode   # build + package .vsix into ./releases
npm run publish:all        # build:ext:vscode + publish:vscode + publish:ovsx
./publish.sh               # interactive version of the publish flow, prompts for tokens
```

There is no automated test suite. Verification is: `npm run build` succeeds, `npx tsc --noEmit` is clean, then manually launch the Extension Development Host (F5, uses `.vscode/launch.json`) and eyeball at least one dark/light/HC theme across JS/TS/Python/Markdown/CSS.

## Architecture

**`src/shared/theme-registry.ts` is the single source of truth.** It exports `themeRegistry: ThemeRegistryEntry[]`, an array of `{ name, slug, theme, options }`. Both generators (`src/generators/vscode/index.ts`, `src/generators/zed/index.ts`) iterate this same array — adding a theme here is what makes it exist for both editors. `ThemeOptions` (`light`, `hc`, `desaturateInputs`, `untindedSelection`) is the only per-theme config and gets translated per editor: `getVscodeUiTheme()` maps it to `vs` / `vs-dark` / `hc-black`, `getZedAppearance()` maps it to `dark` / `light`.

**Theme data flows one direction:** a palette file in `src/variations/*.ts` defines a `Theme` (`colors: ThemeColors`, `levels: ThemeLevels`, `ui: ThemeUi`) using `makeMainColorsDark()`/`makeMainColorsLight()` from `src/helper.ts` to derive the full `ThemeUi` from just a base + primary color → registered once in `theme-registry.ts` → consumed by both generators, which map the shared `Theme` onto editor-specific color/token schemas (`src/generators/vscode/types.ts`, `src/generators/zed/types.ts`). Never edit `dist/` — it's fully regenerated by the build.

**The two generators are structurally parallel but independently implemented — nothing is shared between them except the input types.** VS Code: `ui.ts` (UI colors) + `scopes/*.ts` (`prog.ts`, `markup.ts`, `styling.ts` = TextMate scopes, `semanticTokens.ts`) assembled in `generators/vscode/index.ts`. Zed: `ui.ts` + `syntax.ts` assembled in `generators/zed/index.ts`. A change to how a color is derived (e.g. comment color, muted text) must be made in both places by hand; there's no shared helper enforcing parity between them.

**`package.json`'s `contributes.themes` array must be manually kept in sync with `theme-registry.ts`** — VS Code's extension manifest can't read the registry at install time. `generateThemeContributes()` produces the same data as a build artifact (`dist/vscode/themes-contribute.json`) but nothing consumes it automatically; when adding/removing a VS Code theme you must hand-edit `package.json` too, using the theme's `slug` (lowercase, hyphens, `&` kept literal e.g. `black-&-ruby`) to build the `path`.

**Versioning is per-IDE and asymmetric**, defined in `versions.json` (`{vscode, zed}`) via `version-manager.ts`. Zed's version lives *only* in `versions.json`, read through `getVersionConfig()`/`getZedVersion()` and written into `dist/zed/extension.toml` at build time. VS Code's version lives in `package.json` (`%npm_package_version%` is what `vsce`/`gh release`/`publish.sh` all key off), and `npm run bump:version vscode ...` writes both `versions.json` and `package.json` to keep them nominally aligned — nothing enforces that they stay in sync if `package.json` is edited another way.

## Conventions

- Formatting is enforced by ESLint Stylistic (`@stylistic/eslint-plugin` in `eslint.config.js`), not Prettier: double quotes, 2-space indent, 80-col soft limit, trailing commas. Run `npm run fix` before committing.
- `eslint-plugin-perfectionist` alphabetizes imports/object keys/interface members by default. `src/generators/zed/types.ts` is explicitly exempted (logical grouping instead) via an override at the bottom of `eslint.config.js`.
- Colors are always hex strings, manipulated through `colord` (`colord(color).darken()/.lighten()/.alpha()/.mix()`), never raw RGB/HSL math.
- `tsconfig.json` uses `moduleResolution: "bundler"` with an explicit `"types": ["node"]` — TypeScript 6+ no longer auto-includes `@types/node` ambient globals (`process`, `fs`, …) without it; if bare Node globals suddenly stop resolving after a TS upgrade, check that field first.
- `@typescript-eslint` currently caps the usable TypeScript major at 6.x (peer range `>=4.8.4 <6.1.0`) — don't jump `typescript` to 7.x without checking `@typescript-eslint`'s peer range has caught up.
